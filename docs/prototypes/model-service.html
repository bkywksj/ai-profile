为什么「验证」要放在保存之前
原设计只有列表行有测试按钮 —— 意味着用户必须先存一条可能是错的配置才能知道对不对， 错了还要回来编辑。中转站的 base_url 和模型名恰恰是最容易填错的两项。 保存前验证把「试错」收进弹窗内部，一次填对再落库。

失败诊断 —— crate 返回结构化错误，UI 才能给「一键修正」
每一类失败都对应一个可操作动作。这张表直接定义 crate 的错误枚举
错误类型 用户看到的 可操作动作 crate 错误变体
401 / 403 密钥无效或已过期 聚焦到密钥输入框 AuthFailed
404 端点不存在，多半缺版本段 一键补 /v1 NotFound{suggested_url}
超时 / DNS 连不上，可能需要代理 跳到网络设置 Unreachable
模型不在清单 端点可达，但填的模型名它不认 展开可用模型下拉 ModelNotFound{available}
协议不匹配 密钥只接受 /v1/messages 切到 Claude Code 档 ProtocolMismatch{expect}
🔴 这张表是 crate API 的一部分，不是 UI 细节。 如果 crate 只返回 Err(String)，UI 就只能显示一行红字 —— 「一键修正」这类动作必须靠结构化错误才做得出来。 sigil 现有实现已有两个这样的弹窗（密钥解密失败、协议不匹配），正是这条路走通了的证据。
本场景是 v2 新增，也是「该有测试按钮的地方得有」的完整答案。
补按钮只是第一步 —— 真正要定的是：测什么、花不花钱、失败了给什么。 这三问的答案直接决定 crate 的 verify() / dry_run() 两个函数签名和错误枚举，属于阶段 0.6 必须敲定的 API。

crate 侧：kind 挂 feature
# 不用的 kind 不编进二进制
ai-profile = { version = "0.1",
features = ["chat"] } // sigil
features = ["chat","image","video","tts"] }
视频要轮询、配音要音频编解码 —— sigil 不该为用不到的能力付出编译时间和二进制体积。
四种 kind 的执行模型不同
kind执行模型UI 必需
chat同步 / 流式流式开关
image同步 或 submit+poll尺寸 / 张数
video必然 submit+poll进度条 + 取消
tts同步，返回字节流音色 + 试听
不能用一个 trait 抹平。视频每家 poll 协议都不同（Ark GET /tasks/{id}、 硅基流动 POST {requestId}、海螺 GET /query?task_id=） —— 实测自 StoryLoom 现有实现。
「方便代码控制」的落点：kind 是数据不是分支。
组件遍历 config.kinds 渲染区块，表单遍历 preset.extraFields 渲染输入框， 失败提示遍历错误枚举匹配动作 —— 新增一种 kind（比如将来的「音乐模型」）只需在 crate 里加一个枚举值 + 一组预置， 四个应用的前端零改动。写成 if kind == "video" 的分支，每加一种就要改四个应用。
