## 🎨 方案设计与结论

### 第 1 条：生图 `size` —— 不改请求体，只补注释 + 钉住现状的测试

**问题成立**：`ImageRequest` 只有硅基流动的字段名；火山方舟 Seedream、OpenAI 官方认的是 `size`。

**最初方案（已否决）**：照 onestop 的做法同时带 `size` + `image_size`。联网核查后否决，理由：

- 🔴 Seedream 4.5 / 5.0 要求总像素 ≥ 2560x1440（约 369 万）。prism 的 1024x1024、StoryLoom 的 720x1280
  发过去会被拒；**现在不带 `size`，方舟按默认尺寸出图是成功的** —— 双带会把「尺寸不对」变成「出不了图」。
  火山官方已把 5.0 列为 4.0 / 4.5 的首选替代，用户很可能填新模型
- 硅基流动直连时收到多余的 `size` 会不会报错，**没有任何证据**。onestop 那次双带的提交（`a9d7067`）自称
  「参考 story_loom」，但 StoryLoom 历史上（`c1f5624^` 的 `image_provider.rs`）从来只发 `image_size`；
  一旦报错，StoryLoom 在用的 Kolors 直接坏

**本次做的（零风险）**：
- `ImageGenParams::size` 的文档写清「这是请求值，不保证是实际尺寸」，各协议是否生效
- `ImageRequest` 上加警示：别顺手补 `size`，要改先用真实密钥逐家验证
- mock 测试 `openai_image_body_uses_siliconflow_fields_only` 钉住现状（有 `image_size`、没有 `size`）
- prism 侧正确修法（本次不改 prism，记在登记表备注）：素材库尺寸从出图字节读实际宽高，不记请求值

**有密钥后再做**（按端点分请求体；`ImageRequest` 私有，不动公开 API）：
- 硅基流动：保持现状
- 火山方舟：带 `size`；低于该模型下限时**按原比例放大到下限**（720x1280 → 1440x2560，1024x1024 → 1920x1920，
  都是官方推荐尺寸）；认不出的新模型不带 `size`（退回今天的行为）。下限表按模型 id 放 crate（随服务商变）
- OpenAI 官方：只发 `model` / `prompt` / `size` / `n`
- 中转 / 自定义：保持现状（new-api 的硅基渠道认 `image_size`，`size` 只在 `image_size` 为空时才用）
- 需付费验证：方舟 4.0、4.5 各出一张；OpenAI 出一张（要代理）

### 第 2 条：按能力反推预置 —— 进 crate，新增 `preset::infer_preset_key_for`

**问题成立**：`infer_preset_key` 只遍历 `presets_for(Kind::Chat)`，这是故意的
（守卫 `infer_preset_key_only_returns_chat_presets`，防同 host 的对话配置被认成生图档）。

**归属判定（crate-boundary）**：目前只有 prism 用（StoryLoom / onestop 不存 `preset_key`），但仍放 crate：
- 换一个应用接入「生图配置 + 粘贴导入」，要原样再写一遍
- prism 的副本靠「`base_url` 为空且 `match_hosts` 为空」找自定义档 —— 这是 crate 预置的内部约定，
  对话预置里已有 3 条符合（`claude_code` / `codex` / `openai_compatible_custom`），生图现在碰巧只有一条。
  crate 以后给生图加个中转档，prism 就会静默认错 —— 随预置变化而变，属 crate

**签名**：`infer_preset_key_for(kind: Kind, protocol: Protocol, base_url: Option<&str>) -> &'static str`
- 对话：原样委托 `infer_preset_key`；其余：只在该能力的预置里按 `match_hosts` 认，认不出 → 该能力的自定义档
- 保留 `protocol` 参数：调用方一行搞定，不用按能力分支（prism 的 `import_preview` 就是这种写法）
- 命名对齐 `presets_for(kind)`；不改 `infer_preset_key`（改签名 = 破坏性）；自定义档 key 不新增公开常量

**版本位**：新增公开函数 → 表中 minor → 0.x 补丁位。纯新增，下游不用改；prism 升级时删 `infer_image_preset_key`。

### 第 3 条：按能力分类模型 —— 不做，只记录

**问题成立**：`NON_CHAT_MARKERS` 不分类；prism 列的 5 个样本各命中一个词（`bge-` / `rerank` / `cosyvoice` /
`sensevoice` / `kolors`）。不只 prism：StoryLoom 生图 / 视频 / 配音三种下拉都把 `dropped_models` 排最前，onestop 接在对话后面。

**不做 `model_kind(id) -> Option<Kind>` / `VerifyOk` 分组的理由**：
- 拿它挑生图候选 = 白名单：名字不带现有特征词的真实生图模型会被藏掉（智谱 cogview-4、HiDream-I1、HunyuanDiT），违反铁律 3
- `Kind` 里没有向量 / 重排 / 转写，`None` 同时表示「不认识」和「向量」，调用方没法按排除法用
- 按名字「只排序、不删」虽不误藏，但要把 `NON_CHAT_MARKERS`（公开常量、原样导出到 `spec/` 的 `rules`）拆成分类表，
  还要定类别互斥规则；手上只有一份硅基流动样本

**更好的方向（有密钥后立项，验证零成本）**：硅基流动 `/models` 官方支持 `type`（text / image / audio / video）
与 `sub_type`（chat / embedding / reranker / text-to-image / …）筛选 —— 厂商自己的分类，不用猜名字。
设想：预置加可选字段（`siliconflow_image` = `type=image`、`siliconflow_video` = `type=video`）+ `ServiceConfig::with_models_query`，
没声明的预置行为不变。缺口：`sub_type` 没有 text-to-speech，配音用 `type=audio` 会带进转写模型。
验证：拿密钥调一次 `/models?type=image`，不花钱。
