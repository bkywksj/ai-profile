## 🎯 核心结论：先设计界面，但不实现界面

> 这是本轮最重要的决策，单独成段。

### 结论

**必须先设计界面（列清交互契约），但第一阶段不写任何 UI 代码。**

### 为什么"先设计界面"不是多此一举

crate 的 API 边界**由消费方决定**。不先想清楚 UI 要什么，struct 的字段就会缺 —— 而
struct 字段是破坏性变更，加一个就要所有接入方跟着改。

reeve 的 `ProviderPreset` 是现成证据，它有三个**纯粹为 UI 存在**的字段：

| 字段 | 为什么存在 | 不先想 UI 会怎样 |
|---|---|---|
| `label_key` + `label` **两份** | 桌面端接了 i18n 用 key，移动端没接 i18n 用纯文本 | 只留 key，移动端接入时才发现要加字段 |
| `group_key` | 下拉要分组（16 家平铺找不到） | 只给平铺数组，UI 只能自己硬编码分组映射 |
| `match_hosts` | 「编辑已有配置时回填模板」这个交互要按 host 反推 | 只能全串比较，base_url 一变格式老配置全掉进「自定义」 |

这三个字段**都不是数据本身需要的**，是 UI 需要的。数据结构的形状由消费者决定 ——
这是接口设计的基本原则，不是这个项目的特殊情况。

### 正确顺序

```
1. 列清四个应用的 UI 交互需求（不画像素，列交互）
        ↓ 反推
2. 定义 crate 的 API（struct 字段 / 函数签名）
        ↓
3. 写 crate + 测试
        ↓
4. sigil 接入验证
        ↓ crate 稳定后
5. 再抽 npm 包（headless hook + 预制组件）
```

### 为什么 UI 包放第二阶段

- crate 未稳定就抽 UI，crate 一改 UI 跟着返工
- UI 层是**可选**的：给了 headless hook，各家不用预制组件也能自己画
- 第一阶段收益已经足够大（预置数据 + 协议 + 端点逻辑统一）

## 🎨 架构设计

### 分层与归属（决定什么进 crate、什么不进）

| 层 | 内容 | 变动频率 | 跨应用差异 | 归属 |
|---|---|---|---|---|
| **L1 预置数据** | 16 家 provider、模型 id、base_url、协议类型 | **极高**（模型月月换代） | **零** | ✅ crate |
| **L2 协议** | `ai.profile` 格式定义 + 解析/生成 | 低 | **零** | ✅ crate |
| **L3 端点逻辑** | URL 拼接、鉴权头、chat/stream/test/fetch_models、错误映射、模型清单清洗 | 中 | 小 | ✅ crate（客户端部分挂 feature） |
| **L4 存储** | 密钥加密、CRUD、active 切换 | 低 | **大**（sigil 是 SQLCipher 金库，别家各不同） | ❌ 留给应用 |
| **L5 表单 UI** | 下拉、获取模型、粘贴导入 | 中 | 中（令牌命名不同，组件库同构） | ⏸ 第二阶段 npm 包 |

**最痛的恰好是 L1** —— 变动最频繁、差异为零。L4/L5 差异大、变动少，投入产出比最低。
**追求「整块封装」是这个问题上最容易犯的错。**

### UI 栈同构性（2026-09-22 实测，推翻了先前判断）

| | antd | react | tailwind | zustand |
|---|---|---|---|---|
| sigil | 6.3.1 | 19.1.0 | 4.2.1 | 5.0.11 |
| reeve | 6.3.1 | 19.1.0 | 4.2.1 | 5.0.11 |
| knowledge_base | 6.3.1 | 19.1.0 | 4.2.1 | 5.0.11 |
| tauri-cc | 6.3.1 | 19.1.0 | 4.2.1 | 5.0.11 |

**版本号完全一致**，共享 React 组件技术上可行。

真正的差异只有**设计令牌命名**：

```
sigil      --bg-primary    --text-1      --border
reeve      --color-bg-ink  --color-line  --color-primary
tauri-cc   --completed     --diff-add    （另一套）
```

**解法**：共享组件只用 antd 组件 + `token.*`，不碰任何 CSS 变量 ——
四家本来就各自在做 `antdTheme.ts` 这层映射，组件自动跟随各家主题。

实测 sigil 那个 1096 行的表单组件**只有 26 处硬引用 CSS 变量、涉及 14 个令牌**，
全部能一一映射到 antd token：

| CSS 变量 | antd token |
|---|---|
| `--text-tertiary` / `--text-3` | `colorTextTertiary` |
| `--text-1` / `--text-primary` | `colorText` |
| `--text-2` / `--text-secondary` | `colorTextSecondary` |
| `--divider` | `colorSplit` |
| `--bg-hover` | `controlItemBgHover` |
| `--warning` | `colorWarning` |
| `--primary` | `colorPrimary` |
| `--border-strong` | `colorBorder` |

改完这 26 处，组件零外部依赖。

### 为什么开源

上一轮识别出的最大落地障碍是**跨仓库依赖怎么拉**：私有仓 + cargo git 依赖认证 +
五个项目 CI 都要配 PAT，每一环都是真实的坑（见 CLAUDE.md 的 git 凭据约束）。

**开源把这个障碍整个消掉**：`cargo add` / `pnpm add` 直接拉，CI 零配置。

判断能不能开源只看一件事：**里面有秘密吗？** 没有。
provider 清单、base_url、模型 id 全是公开信息；真正的秘密（API Key）在各应用自己的
存储层 —— 而存储层恰好是这个 crate **不包含**的部分（L4）。

> ⚠️ 这与 CLAUDE.md「仓库一律私有」冲突，已由用户 2026-09-22 明确确认开源。
> 姿态：**发布但不运营** —— 不承诺响应 issue、不做推广，把它当「零摩擦的分发渠道」。

### 为什么 `preset/` 要拆成目录

原版是单个 `presets.rs`。但 image/video/tts 都挂 feature，塞在一个文件里要写满
`#[cfg(feature = "...")]`，而且「加一家 provider 只改一处」会退化成
「在 500 行里找位置」。按 kind 分文件后，加一家 chat provider 只碰 `preset/chat.rs`。

### 为什么单仓多包（monorepo）而不是两个仓库

- crate 和 npm 包的**版本必须对齐**（npm 包依赖 crate 暴露的数据结构）
- 分仓后改一个协议字段要开两个 PR，且没有原子性
- 单仓可以用一份 CI 同时验证两边

### 🔴 五项补充（第一版就要有，不能等）

| # | 缺什么 | 为什么不能等 |
|---|---|---|
| 1 | **`error.rs` 结构化错误** | 「401→聚焦密钥框 / 404→一键补 /v1 / 模型不存在→展开可用清单」全靠它。返回 `Err(String)` 的话 UI 只能显示一行红字，一键修正做不出来 |
| 2 | **`vendor.rs` 服务商聚合** | 没有 `vendor_id` 就没法把「硅基流动的 chat 预置」和「它的 image 预置」认成同一家，服务商目录的卡片做不出来 |
| 3 | **`docs/providers.md`** | 20 家散在 4 个 Rust 文件里，没有一处能一眼看全。开源后这是 README 之外最该有的文档 |
| 4 | **版本化策略** | 模型 id 变动频繁（DeepSeek 下线别名就是例子）。不先定规则，头三个月会连发几个 major |
| 5 | **`xtask probe`** | 守卫测试只管数据格式，管不了「这 20 家的 base_url 现在还通吗」。**手动触发、不进 CI** —— 否则每次 PR 都打人家的端点 |

### 版本化策略（`docs/versioning.md` 的内容）

| 改动 | 版本位 | 理由 |
|---|---|---|
| 改模型 id / 加 provider / 改 base_url | **patch** | 数据更新，不动 API |
| 加 `Kind` 枚举值 / 加 struct 字段 | **minor** | `#[non_exhaustive]` 保证下游不 break |
| 改 / 删 `ProviderPreset` 已有字段 | **major** | 破坏性 |
| 改 `preset.key` | **major** | 🔴 它是存量配置回填的依据，改名会让用户已存的配置失效 |

> `ProviderPreset` 与所有公开 enum 一律加 `#[non_exhaustive]` —— 这是把「加字段」
> 从 major 降到 minor 的唯一办法，第一版就要加，事后补是破坏性变更。

### 数据可信度：每条预置带 `verified_at`

现在预置里混着两种数据：**核对过的**（sigil 的 `deepseek-flash` 有 2026-09-17 实测注释）
和**照搬的**。开源后别人提 PR 加 provider，没有这个字段就没法判断该不该信。

```rust
pub struct ProviderPreset {
    // …
    /// 最后一次实际调通的日期（YYYY-MM-DD）。空 = 未核实，仅供参考
    pub verified_at: Option<&'static str>,
}
```

UI 上体现为：超过 6 个月未核实的预置，在服务商目录卡片上标一个淡色「久未核实」。

### 核心 struct（草案，待评审）

```rust
#[derive(Debug, Clone, Serialize)]
#[serde(rename_all = "camelCase")]
#[non_exhaustive]                          // 🔴 第一版就加，事后补是破坏性变更
pub struct ProviderPreset {
    /// 模板 key = 下拉 value，也是存量配置回填的依据（🔴 改名 = major）
    pub key: &'static str,
    /// 🔴 跨 kind 聚合的依据。硅基流动的 chat/image/video/tts 共用一个 vendor_id，
    /// 服务商目录靠它把四条预置并成一张卡
    pub vendor_id: &'static str,
    /// 这条预置属于哪种能力
    pub kind: Kind,
    /// 分组 key（i18n）。数组顺序即呈现顺序，同组保证连续
    pub group_key: &'static str,
    /// 分组纯文本名 —— 给没接 i18n 的消费方（knowledge_base）
    pub group_label: &'static str,
    pub label_key: &'static str,
    /// provider 纯文本名。同 group_label 的理由
    pub label: &'static str,
    pub hint_key: Option<&'static str>,
    /// 🔴 含版本段、不含端点后缀。None = 走官方端点 / 用户自填
    pub base_url: Option<&'static str>,
    /// 默认 model；空串 = 让用户自己填（本地推理服务的 id 因人而异）
    pub model: &'static str,
    pub models: &'static [ModelOption],
    /// 实际协议：走 /v1/messages 还是 /v1/chat/completions
    pub protocol: Protocol,
    /// 从已存配置的 base_url 反推模板 key 用的主机名片段
    pub match_hosts: &'static [&'static str],
    /// 专有协议的额外配置字段。UI 遍历它渲染输入框，收集为 JSON 存进 extra
    pub extra_fields: &'static [ExtraField],
    /// API Key 申请页；None = 本地服务，不需要申请
    pub apply_url: Option<&'static str>,
    /// 🔴 是否需要用户先在本机把服务跑起来（Ollama / LM Studio / vLLM）
    /// 目录卡片据此区分「云端服务，去申请 key」与「本地服务，先启动它」
    pub is_local: bool,
    /// 最后一次实际调通的日期（YYYY-MM-DD）。None = 未核实，仅供参考
    pub verified_at: Option<&'static str>,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize)]
#[non_exhaustive]
pub enum Kind { Chat, Image, Video, Tts }   // 加枚举值 = minor，不 break 下游
```

### 🔴 结构化错误 —— 「一键修正」的唯一前提

```rust
#[derive(Debug, Serialize)]
#[non_exhaustive]
pub enum VerifyError {
    /// 401 / 403 → UI 聚焦到密钥输入框
    AuthFailed { detail: String },
    /// 404 → UI 给「一键补 /v1」按钮
    NotFound { requested_url: String, suggested_url: Option<String> },
    /// 超时 / DNS → UI 提示去网络设置配代理
    Unreachable { proxy_hint: bool },
    /// 端点可达但模型名不认 → UI 展开可用模型下拉
    ModelNotFound { available: Vec<String> },
    /// 密钥只接受 /v1/messages → UI 提示切到 Claude Code 档
    ProtocolMismatch { expect: Protocol },
    /// 必填的 extra_field 没填 → UI 在验证前就禁用按钮
    MissingExtraField { key: String },
}
```

> **如果 crate 只返回 `Err(String)`，上面每一条的「UI 动作」都做不出来。**
> sigil 现有实现已有两个这样的弹窗（密钥解密失败、协议不匹配），
> 是这条路走通了的证据。

## ✅ 两级验证（该有测试按钮的地方得有）

> 原型场景 E。补按钮只是第一步 —— 真正要定的是：**测什么、花不花钱、失败了给什么**。

### 🔴 四种 kind 的测试成本差几个数量级

| kind | 验证连接（零成本） | 试运行（真实调用） | 单次成本 | UI 处置 |
|---|---|---|---|---|

### 验证的五种状态（组件必须都渲染得出来）

| 状态 | 视觉 | 要点 |
|---|---|---|
| ① 未验证 | 灰色虚线 | 🔴 **不显示红色** —— 没验证不等于有问题 |
| ② 验证中 | 主色 + spinner | 按钮同时禁用，防重复提交 |

| ④ 失败 | 红色 + 错误分类 | 必须带分类，不能只说「失败」 |
| ⑤ 不可验证 | 琥珀色 | 必填字段没填，**按钮禁用**而非点了报错 |

### 失败诊断 = 结构化错误 × 可操作动作

见上方 `VerifyError` 枚举。每一类失败对应一个 UI 动作：
401→聚焦密钥框、404→**一键补 /v1**、超时→跳网络设置、

## 🎭 多模态扩展设计（chat / image / video / tts）

> 🔴 **不是我发明的** —— StoryLoom 已有完整的四种 provider 实现，本节是对它的提炼。
> 原型：`docs/prototypes/model-service-multimodal.html`（4 个场景，浏览器实测渲染通过）

### StoryLoom 现有实现（2026-09-22 实测）

```

├── provider.rs        560 行   chat
├── image_provider.rs  623 行   image
├── video_provider.rs 1050 行   video
├── tts_provider.rs    646 行   tts
```

预置数量：chat 9 家 / image 5 家 / video 9 家 / tts 4 家。

### 🔴 关键事实：四种 kind 的执行模型根本不同，不能用一个 trait 抹平

| kind | 执行模型 | trait 方法 | UI 必需 |
|---|---|---|---|
| chat | 同步 / 流式 | `chat()` / `chat_stream()` | 流式开关 |
| image | 同步 **或** submit+poll（因家而异） | `generate()` | 尺寸 / 张数 |
| video | **必然 submit+poll** | `submit()` + `poll()` | 任务进度条 |
| tts | 同步，返回字节流 | `synthesize()` | 音色选择 + 试听 |

而且**视频每家的 poll 协议都不同**（实测自 StoryLoom）：

- 火山 Ark：`GET {base}/tasks/{task_id}`
- 硅基流动：`POST` body `{requestId}`
- 海螺 MiniMax：`GET {base}/query/video_generation?task_id=`

→ crate 必须**按 kind 分 trait**，不能强求一个统一接口。

### 灵活接入的三层机制

**① 应用侧：一行声明**

```rust
// sigil —— 凭据保险库，只要对话
ModelServiceConfig::kinds(&[Kind::Chat])

// storyloom —— 漫剧化全链路
ModelServiceConfig::kinds(&[Kind::Chat, Kind::Image, Kind::Video, Kind::Tts])
```

**② crate 侧：kind 挂 feature**

```toml
ai-profile = { version = "0.1", features = ["chat"] }                      # sigil
ai-profile = { version = "0.1", features = ["chat","image","video","tts"] } # storyloom
```

视频要轮询、配音要音频处理 —— sigil 不该为用不到的能力付出编译时间和二进制体积。

**③ UI 侧：未声明的 kind 完全不渲染**

🔴 **不是灰掉，是不存在**。灰掉是给「暂时不可用」用的；sigil 永远不需要视频模型，
给它一个灰掉的区块等于持续暗示"这里少配了点东西"。

### `extraFields` —— 灵活接入的核心机制

豆包 TTS 要 `appid` + `cluster`，海螺视频要 `group_id`。这类字段**按服务商而非按 kind 变化**
（同是 tts，硅基流动就不需要）。

写死在组件里 = **每接一家新服务商就要改前端**；放进预置表 = 加一家 provider
只改 crate 的一个数组字面量，四个应用同时生效。

```rust
pub struct ProviderPreset {
    // …前述字段…
    pub kind: Kind,                          // 🔴 新增
    /// 专有协议的额外配置字段。UI 遍历它渲染输入框，收集为 JSON 存进 extra
    pub extra_fields: &'static [ExtraField],
    /// API Key 申请页（设置页给个链接，省得用户自己搜）
    pub apply_url: Option<&'static str>,
}
```

### 能力矩阵

| 应用 | chat | image | video | tts | 说明 |
|---|:---:|:---:|:---:|:---:|---|
| Sigil | ✅ | — | — | — | 凭据保险库，AI 助手只需对话 |
| Reeve | ✅ | — | — | — | 远程运维助手 |
| knowledge_base | ✅ | — | — | — | RAG 检索 + 问答 |
| **StoryLoom** | ✅ | ✅ | ✅ | ✅ | 漫剧化：小说 → 分镜 → 视频 → 配音 |

### 判据：kind 是数据，不是分支

组件遍历 `config.kinds` 渲染区块，表单遍历 `preset.extra_fields` 渲染输入框。

**验收标准：新增一种 kind（比如将来的「音乐模型」）时，四个应用的前端应零改动。**
如果写成 `if kind == "video"` 的分支，每加一种就要改四个应用 —— 那就退回了原点。

### 原型落地时的硬约束

1. **颜色全部改用 antd token**（`colorPrimary` / `colorText` / `colorSplit`…），
   不保留原型里的 Tailwind 自定义色 —— 四个应用 CSS 变量命名各不相同，
   只有 antd token 是四家共有的适配层。
2. **kind 区块、extraFields 必须遍历数据渲染**，不是 if/else。
3. **视频轮询实现放在 crate 内**（各家协议不同），组件只消费最终状态。

### 对阶段划分的影响

多模态**不进第一版 crate**。第一版只做 `Kind::Chat`，但：

- `Kind` 枚举、`ProviderPreset.kind` 字段、feature 切分**从第一版就留好**
  （加枚举值是兼容的，改 struct 字段不是）
- 阶段 4（npm 包）的组件从一开始就按「遍历 kinds」写，即使当时只有一种
- StoryLoom 接入排在阶段 6，届时把它现有的 image/video/tts 实现反向搬进 crate
