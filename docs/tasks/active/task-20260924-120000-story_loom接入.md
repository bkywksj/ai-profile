## 🎨 方案（草案）

### 存量地址修正（只动 chat 的 Anthropic 那几条）

- OpenAI 兼容：旧规则 `{e}/chat/completions` 与 crate `join_chat_endpoint` 一致 → **不用改**（DeepSeek 只填主机名照样能用）
- Anthropic（`extra.protocol=anthropic` 或端点含 `anthropic`，与 `from_provider` 同口径）：
  不以 `/v1` 或 `/v1/messages` 结尾的补 `/v1`（含 `https://api.anthropic.com`、`…/proxy/anthropic`）
- 生图 / 视频 / 配音：**不修**，它们的拼接与分发仍在应用侧
- 冻结两条旧规则 + 对照测试；入口只有 v30 迁移（事务内、幂等）

## ❓ 待用户确认

1. **多模态搬进 crate 的范围**：建议**本轮只搬预置（纯数据）**，生图 / 视频 / 配音的 client（submit+poll，约 2300 行）留在 story_loom。
   理由：预置有两家用（story_loom + onestop），立刻有复用价值；client 目前只有 story_loom 在生产里用，搬过去没有第二个消费方，
   却要把各家轮询协议、错误翻译、熔断一起重做一遍，风险高收益低。等 onestop 也要这几家的 submit/poll 时再搬。
2. **一条配置一个模型**：建议**保持单模型、不改表结构**。「获取模型」拉到的清单只作下拉候选。
3. **ai.profile**：建议导入换 crate（支持打包、协议照来源），**新增** ai.profile 导出（只对 chat 有意义）；
   自有 `storyloom-provider-v1` 格式保留（它支持口令加密、能带生图 / 视频 / 配音配置，ai.profile 表达不了）。
4. **上下文超长**：story_loom 的上下文是作品设定 + 前文，不是对话历史。建议**只识别并给出可读提示**（「上下文超出模型窗口，
   请换更大窗口的模型或缩短设定」），**不自动重试** —— 静默砍一半前文会让生成质量悄悄下降，用户不知道为什么。
